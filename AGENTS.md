## Notes

- ESLint is type-aware and slow; `bun run lint` (not `--fix` in a loop) is the reliable check.
- `next build` does **not** run ESLint; lint is a separate `bun run lint`.
- Component styles are Tailwind CSS modules: every `styles.module.css` must start with `@reference "<relative>/app/globals.css";` or its `@apply` will not resolve. `src/app/globals.css` deliberately omits Tailwind preflight (the app ships its own reset).
- The proxy matcher in `src/proxy.ts` must stay a plain string constant (Turbopack requirement); `unicorn/prefer-string-raw` is disabled for that file in `eslint.config.mjs`.
- `src/lib/db/auth-schema.ts` is generated by Better Auth CLI and lint-ignored; don't edit by hand.
- Server actions need `bodySizeLimit` (5 MB) for photo uploads — configured in `next.config.ts`.
- The plant photo Route Handler lives at `src/app/(app)/plants/[id]/photo/route.ts`, not under `/api`. That path is the stored `Plant.photo` URL produced by `queries.rowToPlant`; route groups scope layouts, not Route Handlers.
- **No `next/image`** (deliberate deviation): the `requireUser()`-gated `bytea` photo route can't be read by the Image Optimizer because it forwards no cookies, and the two capture-preview `<img>` sites use unsupported `blob:` URLs. Keep `PlantPhoto` and the previews as plain `<img>`.
- **Font** is self-hosted Manrope via `next/font/local` in `src/app/layout.tsx` (loader inlined there, not `next/font/google`): `--font-manrope` is wired to `--font-sans` in the `@theme static` block. Never add a runtime Google font request.
- **Boundary model:** `(app)/error.tsx` does not catch `(app)/layout.tsx` errors (they reach the root `error.tsx`); `src/app/global-error.tsx` covers root-layout failures; `(app)/loading.tsx` covers the page's data fetch but not the auth gate (`requireUser()` reads `headers()`, which blocks navigation before the loading boundary).
- **Auth: Better Auth stays; Keycloak is deliberately not adopted** (decided 2026-09-17). This is a **deliberate deviation from the global `frontend-code-conventions` skill**, which names Keycloak as the auth layer for every app. Per-app auth is a decision, not a default: the apps after Sprout each get their own auth and do not need SSO between them. That removes Keycloak's whole value proposition (centralization) without removing the per-app integration work — `requireUser()`, the proxy check and the session wiring survive either way, because an app stays a thin OIDC client — so Keycloak would add a JVM, a second datastore, ~1.25 GB RAM, a second upgrade cadence and a shared point of failure across every app, to avoid only credential handling. Better Auth is the lighter fit and deploys wherever the app does, including serverless. **Accepted consequences:** no SSO between apps, no admin console, no audit log, no built-in brute-force lockout, and MFA only via Better Auth's `two-factor` plugin plus our own enrolment UI. The discipline that replaces a shared IdP is reusing **one auth pattern** across apps (one `requireUser()` contract, one session config, one password policy). **Revisit when either:** (a) a concrete MFA / LDAP / compliance driver appears, or (b) work starts on the **next app** — at which point evaluate a **separately-hosted shared Keycloak** (one instance, a realm per app, **no SSO required**, ~$5–10/mo on a small VPS) *before* app #2 or #3 ships, since that is the last cheap moment. Not on the "no SSO" premise alone: without SSO a shared instance still pays off by removing per-app credential handling, password reset, email verification, MFA, brute-force lockout, audit events and the admin console, plus one Google IdP config instead of one per app — though it does **not** shrink per-app code, because each app keeps an OIDC redirect, token validation and the cookie/session layer a server-rendered app needs, and it creates one shared failure domain (Keycloak down ⇒ every app down). **Switch cost scales with app count *and* accumulated user data**, so the cheapest moment to reverse this was Sprout itself (declined on purpose) and the next cheapest is before the second app ships — not after the fifth.
- **JWT / bearer-token auth: investigated and NOT adopted** (2026-09-17). Sprout stays on DB-backed cookie sessions; three findings here are worth not re-deriving. (1) **`bearer()` does not validate JWTs** — it accepts Better Auth's *opaque session token* and rewrites it into the `session_token` cookie, so a `jwt()`-issued token fails its HMAC check; the two plugins are not interoperable in the direction you would expect. (2) **`jwt()` is not a session replacement** — its `/token` endpoint requires an existing session, and it needs durable key storage (the `jwks` table, or a custom `adapter`). (3) **Cookie-only ("stateless") sessions are impossible while a database adapter is configured**: `hasServerSessionStore = !!database || !!secondaryStorage` has no override, `session.storeSessionInDatabase` only applies when `secondaryStorage` is set, `cookieCache` is only a cache over a DB-backed row (a read still happens on miss/expiry), `getAccessToken` forces a cache bypass when stateful, and dropping the database is off the table anyway because `plants.userId` FKs `user.id` with `onDelete: 'cascade'`. **Consequence:** the only way to move sessions out of Postgres is `secondaryStorage` (Redis) — a new container, to save one indexed lookup on a table we already have. **JWKS has no consumer here** (no second client), so `jwt()` would add a table plus rotation config to enable verification that nothing performs. Verified against Better Auth v1.7.5 source; the option names and the "stateless only without a DB" semantics also hold in the pinned 1.6.29.
- **Server timezone: deliberately no `TZ` env var** (2026-09-19). Vercel **reserves** `TZ` (with `NOW_REGION`, `AWS_*`, `LAMBDA_*`), so it cannot be set from the dashboard or the CLI — but nothing needs it, and the care engine must not be "fixed" by adding one. The server only ever does arithmetic on **absolute instants**: `dueTasks`/`nextDue`/`daysUntil`/`formatDue`/`formatDaysAgo` compare and subtract `Date.now()` against stored `lastCare + interval` timestamps, so they are timezone-independent and correct on a UTC host. The timezone-*dependent* helpers are `toDateValue`, `startOfToday`, `resolveLastCare` and `today(getLocalTimeZone())`, and `toDateValue` provably differs per process zone: `1789768800000` (19 Sep, local midnight) is `2026-09-19` under `TZ=Europe/Amsterdam` but `2026-09-18` under `TZ=UTC`, because `lastCare` is stored at *local midnight* — 22:00 UTC the previous day. That never reaches server-rendered HTML: every `toDateValue` call site (`CareStatValue`, `CareLogRow`) sits inside `BasePopover.Portal` with no `keepMounted`, so the popup is absent from the initial HTML and renders client-side in the browser's zone; the writes (`startOfToday()`, `parseDate(...).toDate(getLocalTimeZone())`) run in click handlers in the browser; and the `max` dates in `LastCareFields`/`CareLogRow` are consumed only inside client-navigated forms and popups. `getLocalTimeZone()` is therefore deliberate and correct here — pinning a fixed app timezone would be a behaviour change, not a fix. **Accepted residual:** a date picker's `max` can be a day stale between 00:00–02:00 Europe/Amsterdam, only in the client-navigated add/edit forms, and it is recomputed client-side on interaction. Related build fact: `next.config.ts` gates `output: 'standalone'` behind `process.env.VERCEL`, because Next 16.3.x + `standalone` breaks Vercel builds (`ENOENT .next/next-server.js.nft.json`); `.github/workflows/deploy.yml` sets `VERCEL=1` explicitly on the build step because Vercel exposes `VERCEL` only when the project's "Enable access to System Environment Variables" toggle is on, so the guard must not depend on that toggle.
- **PWA cache invalidation is keyed to the deployed commit, and lives in code — not in `deploy.yml`** (2026-09-19). The service worker's cache name is `sprout-<BUILD_ID>`, derived from the `?v=` query string on the registration URL (`public/sw.js` reads `location.search`) rather than a hand-bumped literal. `SiteCore` registers ``/sw.js?v=${BUILD_ID}``, where `BUILD_ID` is `NEXT_PUBLIC_BUILD_ID` inlined at build through `next.config.ts`'s `env` block (`NEXT_PUBLIC_BUILD_ID ?? VERCEL_GIT_COMMIT_SHA ?? 'dev'`); `.github/workflows/deploy.yml` sets it to the deployed commit SHA. This works because the spec's update check skips re-installation only when the script URL **and** the body bytes are both unchanged, so a changed query string alone forces a new worker — whose existing `activate` handler deletes every cache whose name is not current. Verified in a browser: seeding `sprout-OLDSTALE` + `sprout-verify123` and then registering `?v=verify456` left exactly `['sprout-verify456']`. **Do not** "simplify" the registration back to a bare `/sw.js`, and **do not** fingerprint the worker's filename (the byte-comparison then has no stable URL to compare against) — either mistake freezes the shell cache across deployments, which is exactly how a change to `manifest.ts` or an icon would never reach an installed PWA. A `deploy.yml` step cannot do this on its own: Cache Storage lives on the user's device, so only the worker can purge it.
- **`vercel pull` writes `[SENSITIVE]` placeholders, so the prebuilt deploy supplies its own build-time env** (2026-09-19). `vercel pull` downloads the project's env into `.vercel/.env.production.local`, but Vercel refuses to hand back any variable marked **Sensitive** — it writes the literal string `[SENSITIVE]` instead. `next build` then evaluates `betterAuth()`, which validates `BETTER_AUTH_URL` at module scope and throws `Invalid base URL: [SENSITIVE]` while prerendering `/_global-error`, failing the whole build. `process.env` wins over that file, so `.github/workflows/deploy.yml` sets real `DATABASE_URL` / `BETTER_AUTH_SECRET` / `BETTER_AUTH_URL` on the `vercel build` step; runtime still reads the project's own env on Vercel, so a placeholder secret there is harmless. **Do not delete those three vars as redundant** — they are what keeps the build alive, and any future module-scope `process.env` read that validates its input will need the same treatment. Note also that `vercel build` *requires* `pull` first (it otherwise fails with `No Project Settings found locally`), so the step cannot simply be dropped, and `VERCEL_ORG_ID`/`VERCEL_PROJECT_ID` alone are not enough for it. The same placeholder reaches the *browser* through prerendered pages: `/login` and `/signup` were `○ (Static)` in the build's route table and read `process.env.GOOGLE_CLIENT_ID` in a server component, so the generated HTML shipped a Google Sign-In button whose client id was the literal `[SENSITIVE]` — a 403 from `accounts.google.com` on every visit, instead of the intended "Google sign-in is unavailable right now" notice. Both pages now declare `export const dynamic = 'force-dynamic'` so the id is read at request time; any future prerendered page that reads an env var marked Sensitive needs the same treatment, and the `export const dynamic` line must not be removed as a "needless optimisation".
- **ADRs are retired — do not cite or create them.** The Nygard-format records that used to live in `README.md` (ADR-0001 … ADR-0011) were deleted in `c3fc1b7` when the README was rewritten to its current 90 lines, and they are not being reinstated. Any surviving `ADR-00xx` reference in gitignored `.omo/` scratch is historical and points at nothing. Deliberate decisions — **including deviations from the global skills** — are recorded in this Notes section instead (see the Auth note above, plus the `no next/image` and font notes).
