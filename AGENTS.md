- **Auth: Better Auth stays; Keycloak is deliberately not adopted** (decided 2026-09-17). This is a **deliberate deviation from the global `frontend-code-conventions` skill**, which names Keycloak as the auth layer for every app. Per-app auth is a decision, not a default: the apps after Sprout each get their own auth and do not need SSO between them. That removes Keycloak's whole value proposition (centralization) without removing the per-app integration work — `requireUser()`, the proxy check and the session wiring survive either way, because an app stays a thin OIDC client — so Keycloak would add a JVM, a second datastore, ~1.25 GB RAM, a second upgrade cadence and a shared point of failure across every app, to avoid only credential handling. Better Auth is the lighter fit and deploys wherever the app does, including serverless. **Accepted consequences:** no SSO between apps, no admin console, no audit log, no built-in brute-force lockout, and MFA only via Better Auth's `two-factor` plugin plus our own enrolment UI. The discipline that replaces a shared IdP is reusing **one auth pattern** across apps (one `requireUser()` contract, one session config, one password policy). **Revisit when either:** (a) a concrete MFA / LDAP / compliance driver appears, or (b) work starts on the **next app** — at which point evaluate a **separately-hosted shared Keycloak** (one instance, a realm per app, **no SSO required**, ~$5–10/mo on a small VPS) *before* app #2 or #3 ships, since that is the last cheap moment. Not on the "no SSO" premise alone: without SSO a shared instance still pays off by removing per-app credential handling, password reset, email verification, MFA, brute-force lockout, audit events and the admin console, plus one Google IdP config instead of one per app — though it does **not** shrink per-app code, because each app keeps an OIDC redirect, token validation and the cookie/session layer a server-rendered app needs, and it creates one shared failure domain (Keycloak down ⇒ every app down). **Switch cost scales with app count *and* accumulated user data**, so the cheapest moment to reverse this was Sprout itself (declined on purpose) and the next cheapest is before the second app ships — not after the fifth.
- **JWT / bearer-token auth: investigated and NOT adopted** (2026-09-17). Sprout stays on DB-backed cookie sessions; three findings here are worth not re-deriving. (1) **`bearer()` does not validate JWTs** — it accepts Better Auth's *opaque session token* and rewrites it into the `session_token` cookie, so a `jwt()`-issued token fails its HMAC check; the two plugins are not interoperable in the direction you would expect. (2) **`jwt()` is not a session replacement** — its `/token` endpoint requires an existing session, and it needs durable key storage (the `jwks` table, or a custom `adapter`). (3) **Cookie-only ("stateless") sessions are impossible while a database adapter is configured**: `hasServerSessionStore = !!database || !!secondaryStorage` has no override, `session.storeSessionInDatabase` only applies when `secondaryStorage` is set, `cookieCache` is only a cache over a DB-backed row (a read still happens on miss/expiry), `getAccessToken` forces a cache bypass when stateful, and dropping the database is off the table anyway because `plants.userId` FKs `user.id` with `onDelete: 'cascade'`. **Consequence:** the only way to move sessions out of Postgres is `secondaryStorage` (Redis) — a new container, to save one indexed lookup on a table we already have. **JWKS has no consumer here** (no second client), so `jwt()` would add a table plus rotation config to enable verification that nothing performs. Verified against Better Auth v1.7.5 source; the option names and the "stateless only without a DB" semantics also hold in the pinned 1.6.29.
- **Server timezone: deliberately no `TZ` env var** (2026-09-19). Vercel **reserves** `TZ` (with `NOW_REGION`, `AWS_*`, `LAMBDA_*`), so it cannot be set from the dashboard or the CLI — but nothing needs it, and the care engine must not be "fixed" by adding one. The server only ever does arithmetic on **absolute instants**: `dueTasks`/`nextDue`/`daysUntil`/`formatDue`/`formatDaysAgo` compare and subtract `Date.now()` against stored `lastCare + interval` timestamps, so they are timezone-independent and correct on a UTC host. The timezone-*dependent* helpers are `toDateValue`, `startOfToday`, `resolveLastCare` and `today(getLocalTimeZone())`, and `toDateValue` provably differs per process zone: `1789768800000` (19 Sep, local midnight) is `2026-09-19` under `TZ=Europe/Amsterdam` but `2026-09-18` under `TZ=UTC`, because `lastCare` is stored at *local midnight* — 22:00 UTC the previous day. That never reaches server-rendered HTML: every `toDateValue` call site (`CareStatValue`, `CareLogRow`) sits inside `BasePopover.Portal` with no `keepMounted`, so the popup is absent from the initial HTML and renders client-side in the browser's zone; the writes (`startOfToday()`, `parseDate(...).toDate(getLocalTimeZone())`) run in click handlers in the browser; and the `max` dates in `LastCareFields`/`CareLogRow` are consumed only inside client-navigated forms and popups. `getLocalTimeZone()` is therefore deliberate and correct here — pinning a fixed app timezone would be a behaviour change, not a fix. **Accepted residual:** a date picker's `max` can be a day stale between 00:00–02:00 Europe/Amsterdam, only in the client-navigated add/edit forms, and it is recomputed client-side on interaction. Related build fact: `next.config.ts` gates `output: 'standalone'` behind `process.env.VERCEL`, because Next 16.3.x + `standalone` breaks Vercel builds (`ENOENT .next/next-server.js.nft.json`); `.github/workflows/deploy.yml` sets `VERCEL=1` explicitly on the build step because Vercel exposes `VERCEL` only when the project's "Enable access to System Environment Variables" toggle is on, so the guard must not depend on that toggle.
- **PWA cache invalidation is keyed to the deployed commit, and lives in code — not in `deploy.yml`** (2026-09-19). The service worker's cache name is `sprout-<BUILD_ID>`, derived from the `?v=` query string on the registration URL (`public/sw.js` reads `location.search`) rather than a hand-bumped literal. `SiteCore` registers ``/sw.js?v=${BUILD_ID}``, where `BUILD_ID` is `NEXT_PUBLIC_BUILD_ID` inlined at build through `next.config.ts`'s `env` block (`NEXT_PUBLIC_BUILD_ID ?? VERCEL_GIT_COMMIT_SHA ?? 'dev'`); `.github/workflows/deploy.yml` sets it to the deployed commit SHA. This works because the spec's update check skips re-installation only when the script URL **and** the body bytes are both unchanged, so a changed query string alone forces a new worker — whose existing `activate` handler deletes every cache whose name is not current. Verified in a browser: seeding `sprout-OLDSTALE` + `sprout-verify123` and then registering `?v=verify456` left exactly `['sprout-verify456']`. **Do not** "simplify" the registration back to a bare `/sw.js`, and **do not** fingerprint the worker's filename (the byte-comparison then has no stable URL to compare against) — either mistake freezes the shell cache across deployments, which is exactly how a change to `manifest.ts` or an icon would never reach an installed PWA. A `deploy.yml` step cannot do this on its own: Cache Storage lives on the user's device, so only the worker can purge it.
- **`vercel pull` writes `[SENSITIVE]` placeholders, so the prebuilt deploy supplies its own build-time env** (2026-09-19). `vercel pull` downloads the project's env into `.vercel/.env.production.local`, but Vercel refuses to hand back any variable marked **Sensitive** — it writes the literal string `[SENSITIVE]` instead. `next build` then evaluates `betterAuth()`, which validates `BETTER_AUTH_URL` at module scope and throws `Invalid base URL: [SENSITIVE]` while prerendering `/_global-error`, failing the whole build. `process.env` wins over that file, so `.github/workflows/deploy.yml` sets real `DATABASE_URL` / `BETTER_AUTH_SECRET` / `BETTER_AUTH_URL` on the `vercel build` step; runtime still reads the project's own env on Vercel, so a placeholder secret there is harmless. **Do not delete those three vars as redundant** — they are what keeps the build alive, and any future module-scope `process.env` read that validates its input will need the same treatment. Note also that `vercel build` *requires* `pull` first (it otherwise fails with `No Project Settings found locally`), so the step cannot simply be dropped, and `VERCEL_ORG_ID`/`VERCEL_PROJECT_ID` alone are not enough for it. The same placeholder reaches the *browser* through prerendered pages: `/login` and `/signup` were `○ (Static)` in the build's route table and read `process.env.GOOGLE_CLIENT_ID` in a server component, so the generated HTML shipped a Google Sign-In button whose client id was the literal `[SENSITIVE]` — a 403 from `accounts.google.com` on every visit, instead of the intended "Google sign-in is unavailable right now" notice. Both pages now declare `export const dynamic = 'force-dynamic'` so the id is read at request time; any future prerendered page that reads an env var marked Sensitive needs the same treatment, and the `export const dynamic` line must not be removed as a "needless optimisation".

- **iOS ignores `box-sizing` on the native date control, so the pickers are sized with `-webkit-fill-available`** (2026-09-20). On iPhone the three `LastCareFields` date inputs overflowed the card and ran 11px past the viewport edge while every desktop browser looked correct. Measured on-device: `input=388 parent=361 vw=393 box=content-box` — `width: 100%` resolved to the parent's 361px and the padding (12+12) plus the border (1.5×2) were added **on top**, 27px in total. This is not a cascade problem and not a missing reset: `globals.css` ships `* { box-sizing: border-box }`, that rule is present in the deployed chunk, and an **inline, non-`!important` `box-sizing: border-box` is ignored too**; `width: 50px` does shrink the field to 50px, so it is not an intrinsic minimum either. The native control simply does not honour `box-sizing` on iOS. `DatePicker/styles.module.css` therefore sets `input { width: -webkit-fill-available }`, which measures 361 on iOS and resolves to the same available width as `w-full` elsewhere — engines that do not recognise the value drop it and fall back to `w-full`. **Do not** replace it with `box-sizing: border-box` or delete it as redundant: both were measured on the device and leave the 27px overflow in place. `appearance: none` also reaches 361 but is rejected — it strips the native control and runs into WebKit bug 198959, where an empty date input collapses in height unless `::-webkit-date-and-time-value` is given a height, so it trades a width overflow for a height bug. Two adjacent facts that are **not** defects and must not be "fixed": iOS renders **no calendar indicator** on date inputs (a Chromium-only affordance), and it renders an **empty date input as completely blank** — there is no date-input placeholder to style, `::placeholder` cannot target it, and the `content: attr(placeholder)` workaround needs JS to detect the empty state. Empty-state guidance belongs in the existing `hint` prop (`AddPlantForm` already passes `LAST_CARE_HINT`), which reads the same on every platform.
- **Do not add `capture` to the photo-upload file input** (2026-09-20). `CaptureStage`'s hidden `<input type="file" accept="image/*">` must stay free of `capture`; the attribute reads like a helpful hint, but on iOS it opens the camera app directly and **suppresses the Photo Library / Take Photo / Browse sheet entirely**, so the control labelled "Upload a photo of your plant" cannot reach the library at all. The screen already owns a dedicated live-camera flow (`handleStartCamera`/`handleCapture`), so the input is library-first by design — `capture` would both duplicate the camera and remove the only path to an existing photo. Omitting it fixes the same camera-forcing behaviour on Android.
- **Care defaults are per-genus, sourced from PlantSolve (CC BY 4.0), and live in Postgres — the bundled table is gone** (2026-09-20). `care_reference` holds 134 rows — 76 genera, 37 families and 21 aliases — reduced from a 2026-09-16 snapshot of the [PlantSolve Open Plant Care Dataset](https://www.plantsolve.com); `src/helpers/care/constants.ts` keeps only the hand-authored `FALLBACK_CARE`. The seed is a custom Drizzle migration (`drizzle/0002_seeded_care_reference_table.sql`) applied by the `migrate` job that gates deploy, not a script. PlantSolve is the only source found that carries **all three** cadences — watering, fertilising **and** repotting — under a licence that permits commercial use. **The table lives in Postgres now, and the shape of the access is what keeps that honest.** One 134-row select loads the whole reference per identification and resolution stays an in-memory property access — a per-identification *point* lookup would still be the wrong shape, but there is none. The unique index on (`match_type`, `match_key`) makes the seed idempotent (`ON CONFLICT DO NOTHING`) and curation an `UPDATE` rather than a deploy; Each cadence is stored as a value+unit pair (`water_interval`/`water_unit`, `fertilize_interval`/`fertilize_unit`, `repot_interval`/`repot_unit`) with the unit typed by `CareUnit` (`D`/`M`/`Y`), and the CHECK constraints convert each pair to canonical days inline (`D`=1, `M`=30, `Y`=365) so the horticultural bounds survive (water 2–28, fertilise 14–90 days, repot 6–36 months), replacing the unit tests that asserted those ranges over the generated file — each check requires the pair to be **both NULL or both set**, because `NULL in ('D','M','Y')` evaluates to NULL and a CHECK treats NULL as passing, so a bare unit-membership test lets an interval be stored with no unit (repot was the live case: `repot_interval=2` with a NULL unit lands on 730 days, inside the 180–1095 window, so the range alone did not catch it); the loader (`src/services/server/care-reference/index.ts`) converts the pairs back to the app's `CareSchedule` (`waterEveryDays`, `fertilizeEveryDays`, `repotEveryMonths`) and throws when a genus/family row is missing a value or a unit, so no unit ever reaches the app model. Per-user care rows are a different thing and stay in `plants.care` (jsonb) exactly as before — `care_reference` only *seeds* that column, and it must resolve before any plant row exists. Rejected alternatives, recorded so they are not re-evaluated: **Perenual** is the only source publishing a numeric watering interval (`watering_general_benchmark`, a `"5-7"` string plus `"days"`) but its ToS forbids commercial use *and* derivative works, and it has no fertilise or repot field at all; **FloraDB** has an explicit `watering_frequency_days` for 270 houseplants but its free sample is CC-BY-NC and the commercial set is $49; **OpenPlantBook** returns care as free-text prose with no interval, caps at 200 requests/day, and is a single-maintainer project with no SLA; **Trefle**'s growth fields are Ellenberg wild-habitat classes (1–9 and 1–12, not care preferences) covering 1.4% of species; **Kindwise** offers only an ordinal `watering` (1–3, dry/medium/wet) at 9.5% coverage; **Pl@ntNet** carries zero care fields — confirmed by scanning its entire published `swagger.json`, and its own FAQ points integrators to GBIF for more species data. Two consequences are load-bearing. (1) **`waterEveryDays` is derived, not measured** — PlantSolve publishes no day-count, only `drynessThreshold` (25/50/100) and `growthRate`, so the base is 4/7/14 days modulated ±30% by growth rate and snapped to the existing `WATER_OPTIONS` presets, with ties breaking toward the **longer** interval because overwatering is cumulative and kills while underwatering self-corrects. Fertilise and repot values are parsed from prose ("monthly in spring and summer", "Every 1–2 years"), and the 20 genera with no stated fertiliser frequency are filled by the same growth-rate rule. Note the engine still has one flat interval per kind, so a plant is fed year-round even though the source scopes feeding to spring and summer. (2) **The attribution is a licence obligation, not decoration** — CC BY 4.0 requires a visible credit and a backlink, which is why `SettingsScreen/CreditsCard` exists; do not remove it or the PlantSolve line, and keep each genus row's PlantSolve profile URL in `source_url`. `resolveCare` resolves alias → genus → family → `FALLBACK_CARE`, and logs `No care data for identified plant` on the `CareSource.None` branch only — that log is how real coverage gets measured, and coverage is currently **unmeasured**, so the 76-genus figure is not a hit rate. **`resolveCare` stays pure and synchronous, but takes the loaded `CareReference` as its first argument** — `resolveCare(reference, lookup)` — so it remains unit-testable with a small fixture and never touches the DB. The data access sits behind `src/services/server/care-reference/index.ts`, which carries `import 'server-only'` and is awaited **once per identification**, not once per result; the loader lowercases the family keys when building the map, so `resolveCare` does a plain lookup and no case-insensitive scan. There is **one** alias map now, and the full-name keys are what keep it safe: `Dracaena trifasciata` is an alias row keyed by the full scientific name (redirecting to `sansevieria`) while `Dracaena fragrans` resolves through the `dracaena` genus row, so collapsing species entries into bare-genus keys would silently corrupt corn plants. The old alias guard test went with the bundled table; the unique index on (`match_type`, `match_key`) is what keeps each alias a single row, and the species-then-genus lookup order is what keeps the two meanings apart. The `AddPlantForm` hint is correspondingly three-state (genus / family / none) and must not be collapsed back to one string: the previous "based on the identified species" copy was an unsourced claim the app could not back.

- **Functions run in `fra1` (Frankfurt), pinned in `vercel.json` — not Vercel's Hobby default `iad1`** (2026-09-20). Vercel places every new project's functions in Washington DC (`iad1`), which puts a ~90 ms-each-way detour in front of *every* request for a user in Europe — a ~200 ms floor that no amount of query tuning can remove. The tell was in the response header: `x-vercel-id: fra1::iad1::…`, i.e. the Frankfurt edge handing off to a US function, with a warm `/login` (which touches no database at all) measuring 200–550 ms TTFB from Amsterdam. `vercel.json`'s `regions: ["fra1"]` puts function execution in the same city as the Neon database, which cuts that floor to **62–68 ms** warm (measured from Amsterdam on a reused connection, down from 200–550 ms); verify with `curl -sI https://sprout.radualex.me/login | grep x-vercel-id` and expect `fra1::fra1`, or read `regions` off the deployment object. **Hobby allows exactly one function region** (Pro allows 5), so there is no multi-region failover — but there never was, so nothing is traded away here. The file is the source of truth rather than the dashboard setting because `vercel.json` travels through CI's `vercel pull` → `vercel build --prod` → `deploy --prebuilt` path and cannot drift from the commit. **`Settings → Functions → Function Regions` is a different thing and must not be read as the effective region**: it is the *project default*, it does not update to reflect a `vercel.json` override, and it still read `iad1` while every deployment ran in `fra1`; it was set to `fra1` too on 2026-09-20 so the two agree, but the deployment's `regions` field — and the deployment's Resources tab — is what reports where functions actually run. **Do not** delete `vercel.json` as redundant, and **do not** move functions back to `iad1`: a US region only pays off if the database moves with it, and Neon is already in Frankfurt — splitting them re-creates the same ~90 ms hop on *every* database round trip, of which an authed page makes at least two (`requireUser()`'s session lookup, then the plants query). **Revisit if** the user base stops being Europe-only: on Hobby that means picking the single region that penalises fewer people.

- **`@neondatabase/serverless`: investigated and NOT adopted** (2026-09-20). Production already runs on Neon — `DIRECT_URL` is the unpooled connection `drizzle.config.ts` migrates through, while the app uses the pooled `DATABASE_URL` — so this was never a migration, it is a driver swap, and the answer is no. The driver replaces TCP with HTTP/WebSockets, which **plain Postgres does not speak**: it cannot connect to the `postgres:16-alpine` container that `docker-compose.yml` and `.env.example` point at, and Neon's own docs say using it locally "requires a local instance of Neon's proxy" — a new container for the dev environment, to replace one that already works. Nothing runs on Edge (there is no `export const runtime = 'edge'` anywhere in `src/`), which is the only thing the driver exists for; Node.js + Fluid compute + the existing `pg` pool is the correct shape here, and the latency it looks like it would fix was already fixed by the `fra1` region move. The cost is not just the import: the `bytea` custom type in `src/lib/db/schema.ts` leans on node-postgres mapping `bytea ↔ Buffer` for free, and that type flows through `types.ts` → `queries.ts` → `readPlantPhoto` → the photo route, so the swap puts every plant photo behind a rework. **Do not** re-add this to the roadmap as a pending optimisation. **Revisit only if** the app moves to the Edge runtime — which is itself the larger decision, and nothing in the app currently argues for it.

- **Web Push over a hosted platform, and the periodic-sync path that never worked** (2026-09-20). Reminders are the product, so the app-closed case had to be solved properly rather than approximated. **`web-push` + a Vercel Cron was chosen over OneSignal** because OneSignal requires its own service worker for delivery (its iOS requirements say so explicitly) and `sw.js` here is hand-written around hard-won rules — the `?v=` BUILD_ID cache invalidation, the RSC-payload guard, never caching documents — so merging a third-party worker into it is the expensive part; `web-push` needed one added listener instead, and keeps delivery out of a third party's hands. **The cron is daily, and that is a match rather than a compromise**: Vercel Hobby permits cron jobs at most once per day with ±59 min precision (anything more frequent fails the deploy), while the engine's de-duplication is already day-granular (`now - lastNotified >= DAY_MS`) against day-granular due dates — so one run per day is exactly the product requirement. The schedule is `0 8 * * *` in `vercel.json` — 09:00–09:59 CET in winter and 10:00–10:59 CEST in summer, picked so the reminder never lands before 9 AM local: a fixed UTC cron cannot hold a local wall-clock hour across DST, and Hobby's ±59 min jitter widens the window on top of that. **The `periodicsync` path was deleted, and it is worth knowing why it never worked**: the handler forwarded a `care-check` message to `clients.matchAll()`, and with the app closed there are no clients, so the message went nowhere — the worker never fetched plants or called `showNotification` itself. It was a no-op in precisely the case it existed for, on the only platform that implements it. The in-app watcher (mount, focus, hourly) stays: it serves the open-app case and cannot double-notify, because both paths write the same `lastNotified` through the day-granular check. **Safari requires the notification to be shown immediately** — Apple's docs state that an invisible push handler gets the permission revoked — so the `push` listener must never defer `showNotification`; and that route must never move to the Edge runtime, because `web-push` needs Node `crypto`. `setVapidDetails` validates its arguments, so it is called inside the handler and never at module scope, which would break `next build` the way `BETTER_AUTH_URL` did. **Needs four env vars in the deployment** — `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`, `CRON_SECRET` — and is inert without them: the app still runs, and reminders fall back to the in-app watcher. **`NEXT_PUBLIC_VAPID_PUBLIC_KEY` must stay Config, not Sensitive** — `vercel pull` redacts every Sensitive var to the literal `[SENSITIVE]`, and because a `NEXT_PUBLIC_` value is inlined at build time the client bundle would ship that string as the VAPID key: `decodeVapidPublicKey` throws, `subscribeToPush`'s rejection is swallowed, and push never subscribes with nothing in the logs. Verified 2026-09-20 by pulling the production environment — the Config var returns its real value while the other ten come back as placeholders. That is also why `deploy.yml` needs no change for this feature: the three vars it overrides are build-time reads *and* Sensitive, while the public key is neither.
